# 동역 사이트 제작·운영 가이드

> 용도: 「동역 · 부교역자 라운지」를 어떻게 만들었고 어떻게 설정·운영하는지 정리한 문서입니다. 「KSA 홈페이지 제작·운영 가이드」와 같은 방식(빌드 없는 단일 파일 + GitHub Pages)을 따르되, 정적 호스팅으로는 안 되는 기능(로그인·글쓰기)은 Supabase로 해결했습니다.
> 기준일: 2026-10-07 (마지막 갱신 2026-10-12: Supabase 연결·익명 운영·서울 중계 함수)

| 항목 | 내용 |

| 체험 모드 | `config.js`에 Supabase 값이 비어 있으면 자동으로 「체험 모드」(브라우저에만 저장) |

## 1. 전체 구조

```
[방문자]
   │  https://도메인/  (GitHub Pages)
   ▼
[index.html + config.js + data/jobs.js]  ← 정적 파일
   │
   ├─ 청빙 공고 목록 ── data/jobs.js (하루 3번 자동 갱신·커밋)
   │                     ▲
   │        [GitHub Actions] scraper/fetch-jobs.mjs
   │                     │  제목·날짜·링크만, robots.txt 준수, 3초 간격
   │        신학교·총회·언론·구인 사이트 27곳
   │                     └─ 해외 차단 4곳은 [Supabase 서울 함수 kr-relay]를 거쳐 요청
   │        [맥 launchd] 광신대만 보충 → data/jobs-local.json
   │
   └─ 로그인·교회 평가·대나무숲·자료실·콘티 나눔 ── Supabase
          ├─ Auth: 이메일 링크/6자리 코드 로그인(비밀번호 없음)
          ├─ Postgres: 글·평가·댓글·공감·신고 + RLS(행 단위 보안)
          └─ Storage: 자료실 파일(10MB, 문서·이미지 형식만)
```

**익명성 설계**: 작성자 식별값(`author_id`)은 DB에만 있고, 열 단위 권한으로 막아서 API로는 누구도 읽을 수 없습니다(관리자 화면 포함). 화면에 보이는 익명 이름은 서버가 「작성자+글」로 계산합니다. 같은 글 안에서는 같은 이름이고, 글이 다르면 이름도 다릅니다.

## 2. 제작 방식

### 2-1. KSA 방식과 같은 점
- 단일 `index.html`에 CSS·HTML·JS가 모두 들어 있습니다. 메모장으로 고쳐도 됩니다.
- 화면은 `<div class="page" id="pg-…">`이고, `ALL_PAGES` 배열에 등록합니다.
- 디자인 값은 `:root`의 CSS 변수로 관리합니다. 한글 조판(`keep-all`, `text-wrap`)도 KSA와 같습니다.

### 2-2. KSA 방식과 다른 점(개선)
| 항목 | KSA | 동역 |
|---|---|---|
| 화면 전환 | `go()` + `pushState` | 모든 링크가 `<a href="#pg-…">`이고 `hashchange` 하나로 처리. 뒤로가기·새 탭·링크 공유가 모두 됨 |
| 주소에 값 전달 | 없음 | `#pg-church?name=은혜숲교회`처럼 화면 + 값 |
| 통계 | 첫 진입만 집계되는 문제 | 화면이 바뀔 때마다 `goatcounter.count()` 호출 |
| 설정 | index.html 안에 섞여 있음 | `config.js`로 분리(재사용 쉬움) |
| 동적 기능 | 외부 게시판(아임웹)으로 보냄 | Supabase 연결(없으면 체험 모드) |

### 교회 평가 항목
사례·처우 / 업무량·휴무 / 계약·약속 이행 / 존중·소통 / 담임목사 리더십 / 배움·성장(각 1~5점) + 추천 여부 + 좋았던 점·아쉬웠던 점·후임자에게 한마디. 작성자 보호를 위해 사역 시기는 연도 대신 4단계 구간으로만 받습니다.

### 예배 도구와 세라핌
- 도구 목록은 `config.js`의 `tools`에서 관리합니다. 설치 파일(약 100MB)은 **GitHub Releases**에 올리고 그 주소만 넣습니다. GitHub는 100MB가 넘는 파일을 저장소에 넣을 수 없고, Pages 저장소가 무거워지기 때문입니다.
  - 세라핌 저장소(`hyotowork-create/Seraphim`)는 공개 상태지만 **아직 릴리스가 없습니다.** `Releases → Draft a new release`에서 `Seraphim-0.2.0-arm64.dmg`, `Seraphim-0.2.0-win.zip`(또는 설치본·portable exe)를 올리면 「내려받기」 버튼이 바로 작동합니다. `LICENSE` 파일(MIT)도 함께 넣어 두세요.
- 「세라핌용 파일 받기」는 세라핌의 곡 가져오기 형식인 `{"songs":[{title, category, lyrics}]}`로 저장합니다. 분류는 세라핌과 같은 새찬송가·복음성가·워십·어린이·특송입니다. 가사를 넣은 곡만 세라핌 라이브러리에 들어갑니다.
- 콘티 나눔에는 **가사가 올라가지 않습니다.** 화면에서 빼고 보낼 뿐 아니라, DB도 `lyrics`가 들어 있으면 거절합니다. 찬양 가사·악보 저작권 때문입니다.

## 5. 처음 설정하기

### 5-1. GitHub 저장소·Pages
1. GitHub에서 새 저장소 `dongyeok`(공개)를 만들고 이 폴더 내용을 올립니다.
2. `Settings → Pages → Build and deployment → Source: GitHub Actions`. 배포는 workflow가 맡습니다. main에 올리면 바로 배포되고, 수집 후에도 자동 배포됩니다.
3. `Settings → Actions → General → Workflow permissions → Read and write permissions`에 체크합니다. 자동 수집이 결과를 커밋하는 데 필요합니다.
4. `Actions` 탭에서 「청빙 공고 수집·배포」 → `Run workflow`로 한 번 실행해 봅니다(6-3, 해외 접속 차단 여부 확인).

### 5-2-0. 현재 설정(2026-10-12)
- 프로젝트 `xjmexzeyxkxqsgvwaupz`(조직 dongyeok, Free, 서울). schema.sql 실행 완료. Site URL·Redirect URL = 공개 주소.
- **Allow anonymous sign-ins 켜짐**: 이용자는 로그인 없이 쓰고, 처음 쓸 때 무작위 익명 식별값이 발급됩니다. 이메일 등 개인정보는 받지 않습니다.
- 이메일 로그인은 운영자 전용입니다(관리자 1명). 운영자 계정만 자료 파일을 올릴 수 있습니다.
- Edge Function **`kr-relay`**(서울 중계) 배포됨. 대시보드 → Edge Functions에서 코드·로그를 봅니다(6-3).
- 아래 5-2는 처음부터 다시 만들 때의 절차입니다(이메일 템플릿·SMTP 단계는 익명 운영에서는 필요 없음).

### 5-2. Supabase 프로젝트
1. supabase.com에서 새 프로젝트를 만듭니다. **Region은 `Northeast Asia (Seoul)`**을 고릅니다(속도와 개인정보 국외 이전 최소화).
2. `SQL Editor`에 `supabase/schema.sql` 전체를 붙여 넣고 **Run**.
3. `Authentication → Sign In / Providers → Email`: Email 켜기, **Confirm email 켜기**. 비밀번호 로그인은 쓰지 않습니다.
4. `Authentication → URL Configuration`
   - Site URL: `https://hyotowork-create.github.io/dongyeok/`(도메인 연결 후에는 그 주소)
   - Redirect URLs: 위 주소, 그리고 로컬 확인용 `http://localhost:8765/`
5. `Authentication → Emails → Templates`의 **Magic Link** 템플릿 본문에 6자리 코드를 넣습니다. 카카오톡 같은 앱 안 브라우저에서는 링크 로그인이 실패할 수 있어서 코드 입력을 함께 씁니다.
   ```html
   <h2>동역 로그인</h2>
   <p>아래 링크를 누르거나, 사이트에 6자리 코드를 입력하세요.</p>
   <p><a href="{{ .ConfirmationURL }}">로그인하기</a></p>
   <p>인증 코드: <b>{{ .Token }}</b></p>
   ```
   **Confirm signup** 템플릿에도 같은 내용을 넣습니다(처음 가입하는 사람용).
6. 기본 메일 발송은 시간당 몇 통으로 제한됩니다. 실제 운영 전에 `Authentication → Emails → SMTP Settings`에서 발송 서비스(예: Resend, Gmail SMTP)를 연결하세요.

| 역할 | 방식 | 맡는 출처 | 비용 |

**서울 중계 함수(kr-relay)** — 2026-10-12 배포
- 하는 일: GitHub Actions의 수집기가 `viaKR: true`인 출처에 요청할 때, 서울(ap-northeast-2)에서 같은 식별 UA로 대신 요청하고 응답을 그대로 돌려줍니다. robots.txt 확인·3초 간격·본문 미저장 규칙은 수집기가 그대로 지킵니다. 맥 보충 수집과 같은 성격(한국 회선에서 같은 방식으로 요청)이고, UA 위장·상용 프록시·IP 돌려 쓰기는 하지 않습니다.
- 안전장치(코드 `supabase/functions/kr-relay/index.ts`)
  - 허용한 4개 사이트만 중계합니다. GET만 받고, POST는 총신대 목록 API 한 곳만 받습니다. 넘겨주기(redirect)도 허용 목록 안에서만 따라갑니다. 응답 4MB, 보내는 내용 8KB 제한.
  - 호출 권한: **이 저장소(번호 1415107065) main 브랜치의 GitHub Actions가 발급한 OIDC 토큰**만 받습니다. 비밀키를 따로 두지 않아서 Secrets에 넣을 것이 없습니다. 공개 키(publishable)는 Supabase 관문 통과용일 뿐 권한이 없습니다.
  - 서울이 아닌 곳에서 실행되면 거절합니다(호출할 때 `x-region: ap-northeast-2` 헤더와 `forceFunctionRegion` 값으로 서울 지정).
  - 함수 로그에는 사이트·경로·상태·크기만 남깁니다.
- 수집기 쪽: `scraper/lib.mjs`의 `KrRelay`. 워크플로의 `KR_RELAY_URL`·`KR_RELAY_APIKEY`(둘 다 공개값)와 `id-token: write` 권한이 있을 때만 켜집니다. 맥에서는 쓰지 않습니다. 출처 상태 `note`에 「서울 중계 서버 경유」가 붙습니다.
- 광신대는 서울 함수에서도 실패합니다(학교 서버의 옛 TLS 방식을 Deno가 지원하지 않음: `received fatal alert`). 그래서 맥만 맡습니다.
- 출처를 중계에 더하거나 뺄 때: 소스에 `viaKR: true`를 달고, 함수의 `ALLOW`에도 호스트를 넣어 **다시 배포**합니다. 둘이 다르면 「허용하지 않은 사이트」 오류가 납니다.
- 다시 배포하는 법(대시보드): Supabase → 프로젝트 `xjmexzeyxkxqsgvwaupz` → Edge Functions → `kr-relay` → Code → `index.ts` 전체를 붙여 넣고 Deploy. CLI를 쓴다면 운영자가 `supabase login` 후 `supabase functions deploy kr-relay --project-ref xjmexzeyxkxqsgvwaupz`.
- 점검: `deno test --allow-env supabase/functions/kr-relay/`(함수, 7개) · `node scraper/test-relay.mjs`(수집기, 14개). 둘 다 외부 요청이 없습니다.
- 실서버 확인: 토큰 없이 부르면 401, 미국 지역을 지정하면 421이 나와야 정상입니다.
  ```bash
  curl -s -X POST 'https://xjmexzeyxkxqsgvwaupz.supabase.co/functions/v1/kr-relay?forceFunctionRegion=ap-northeast-2' -H 'apikey: sb_publishable_1cyG9HPpcC4hqJZIv4wbuA_JpoS_UiQ' -H 'x-region: ap-northeast-2' -H 'Content-Type: application/json' --data '{}'
  ```

- 저장소를 옮기거나 새로 만들면: 저장소 번호가 같으면(이름 변경·소유자 이전) 그대로 됩니다. 새 저장소(복사·템플릿)는 번호가 달라 함수의 `REPO_ID`를 바꿔 다시 배포해야 합니다(`gh api repos/소유자/저장소 --jq .id`).

- 공개 저장소는 **60일 동안 활동이 없으면 예약이 꺼집니다.** 수집 결과를 매번 커밋하므로 보통 유지되지만, 한 달에 한 번 Actions 탭에서 최근 실행을 확인하세요. 꺼졌다면 「Enable workflow」를 누릅니다.
- 켜진 출처가 모두 실패하면 작업이 실패로 끝나고, GitHub가 저장소 주인에게 메일을 보냅니다.

**맥에서 자동 실행(launchd)** — 2026-10-12 운영자 맥에 설치함. 광신대와, 직전 GitHub 수집에서 실패한 출처만 보충 수집(`--only=auto --out=local` → `data/jobs-local.json`). 맥이 꺼져 있으면 광신대(약 10건)만 새 공고가 멈추고 나머지는 영향이 없습니다.
- 설치된 것: `~/Library/LaunchAgents/kr.dongyeok.fetch.plist`(05:45·11:45·17:45). 실행하는 사본은 `~/Developer/dongyeok-collector`(git 클론)입니다.
- `~/Downloads` 안의 폴더는 macOS 폴더 보호 때문에 예약 작업이 읽지 못합니다. 그래서 별도 사본을 씁니다.
- 끄기: `launchctl bootout gui/$(id -u)/kr.dongyeok.fetch` · 상태: `launchctl print gui/$(id -u)/kr.dongyeok.fetch`

다른 맥에 새로 설치할 때의 순서(참고):
1. 이 폴더를 GitHub 저장소와 연결된 클론으로 두고(`git push`가 되는 상태), `zsh scripts/mac-fetch-jobs.sh`를 한 번 손으로 돌려 봅니다.
2. `~/Library/LaunchAgents/kr.dongyeok.fetch.plist`를 만듭니다(경로는 실제 폴더로 바꿈).
   ```xml
   <?xml version="1.0" encoding="UTF-8"?>
   <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
   <plist version="1.0"><dict>
     <key>Label</key><string>kr.dongyeok.fetch</string>
     <key>ProgramArguments</key><array><string>/bin/zsh</string><string>/Users/사용자/Developer/dongyeok-collector/scripts/mac-fetch-jobs.sh</string></array>
     <key>StartCalendarInterval</key><array>
       <dict><key>Hour</key><integer>6</integer><key>Minute</key><integer>7</integer></dict>
       <dict><key>Hour</key><integer>12</integer><key>Minute</key><integer>7</integer></dict>
       <dict><key>Hour</key><integer>18</integer><key>Minute</key><integer>7</integer></dict>
     </array>
   </dict></plist>
   ```
3. `launchctl load ~/Library/LaunchAgents/kr.dongyeok.fetch.plist`. 기록은 `scripts/mac-fetch-jobs.log`에 남습니다.
4. 맥은 `data/jobs-local.json`만, Actions는 `data/jobs.json`·`jobs.js`만 커밋하므로 둘을 함께 돌려도 충돌하지 않습니다(커밋 전 `git pull --rebase`).

**수집기 유지보수 스킬**: `.claude/skills/dongyeok-scraper/SKILL.md`에 구조·규칙·고치는 순서를 적어 두었습니다. 이 폴더에서 Claude Code를 열고 "수집이 0건이야"처럼 말하면 그 절차를 따릅니다.

### 6-4. 수집이 0건이 되거나 깨졌을 때(사이트 개편)
1. Actions 로그나 `data/jobs.json`의 `sources[].status/note`를 확인합니다.
2. 해당 게시판 목록을 브라우저로 열어 구조가 바뀌었는지 봅니다.
3. `scraper/sources/○○.mjs`의 선택자(CSS selector)나 API 주소를 고칩니다. 새 목록 페이지를 `scraper/fixtures/`에 저장할 때는 **개인정보를 지운 뒤** 저장합니다. 그다음 `node scraper/test-parsers.mjs`로 확인합니다.
4. `node scraper/fetch-jobs.mjs --only=소스ID --dry`로 실제 수집을 시험해 보고, 문제없으면 커밋합니다.

### 6-5. 출처 추가하기
`scraper/sources/`에 파일 하나를 만듭니다. `{ id, short, name, home, enabled, pages, collect({http}) }` 형태로, 기존 파일을 복사하면 됩니다. 그 파일을 `fetch-jobs.mjs`의 `SOURCES`에 넣습니다. 먼저 robots.txt와 이용약관을 확인하고, 로그인이 필요한 곳은 넣지 않습니다.

## 7. 운영 업무

### 7-1. 매일(5~10분)
- 「운영」 화면 → **검수 대기 교회 평가**: 작성 원칙에 맞으면 「공개」, 고칠 부분이 있으면 「반려」합니다. 반려 사유는 공지로 일반화해 안내합니다.
- **신고된 글**: 내용을 보고 「공개(신고 기각)」·「가림(임시조치)」·「삭제」 중 하나로 처리합니다. 처리 기록은 `moderation_log` 테이블에 자동으로 남습니다.

### 7-2. 평가 검수 기준(공개 / 반려)
| 공개 | 반려(고쳐 쓰기 요청) |
|---|---|
| 처우·업무·소통에 대한 구체적 경험 | 담임목사·성도의 사생활, 가족, 외모 |
| “계약서 없이 시작했고 약속한 사택 지원이 바뀌었다” 같은 사실 진술 | “사기꾼”, “이단” 같은 단정적 비난·욕설 |
| 개선을 바라는 의견 | 범죄 의혹 단정(→ 교단·수사기관 안내) |
| | 다른 교역자 실명, 작성자가 특정되는 사건 |

### 7-3. 권리침해 신고(임시조치) 절차 — 정보통신망법 제44조의2
1. 요청 접수(메일): 해당 글 주소, 침해 내용, 요청인 연락처를 확인합니다.
2. 운영 화면에서 그 글을 **「가림」** 처리합니다(임시조치, 최대 30일).
3. 작성자에게 소명 기회를 줍니다. 작성자 연락처를 공개하지 않으므로, 이용 안내 공지나 해당 글 자리의 안내문으로 알립니다.
4. 30일 안에 **공개 또는 삭제**를 결정합니다.
5. 요청인에게 처리 결과를 회신합니다.
6. 처리 대장(아래 표)에 기록합니다.

| 접수일 | 대상(종류·ID) | 요청인 | 사유 | 조치(가림일) | 결정(일자) | 회신일 |
|---|---|---|---|---|---|---|
| | | | | | | |

> 수사기관의 작성자 정보 요청은 영장 등 적법한 절차가 있을 때만 응합니다. 대응 내역도 기록합니다.

### 7-4. 저작권 삭제 요청(자료실·콘티)
권리자 확인 → 「삭제」 → 파일은 Supabase `Storage → resources`에서 해당 파일을 지움 → 회신. 「삭제」는 화면에서만 숨기는 것이므로 **파일은 Storage에서 따로 지워야 합니다.**

## 9. 다른 단체·모임 사이트로 재사용하기

이 사이트는 **「소개 + 정보 모음 + 익명 게시판 + 자료실」** 형태의 모임 사이트 틀로 그대로 쓸 수 있습니다.

1. **폴더 복사** → 새 GitHub 저장소.
2. **`config.js`**: `name`, `tagline`, `url`, `contactEmail`, `tools`를 바꿉니다.
3. **색·사진**: `index.html` 맨 위 `:root`의 `--night`(바탕)·`--gold`(주요 버튼)·`--violet`(강조)만 바꿔도 분위기가 바뀝니다. 첫 화면·타일·페이지 머리의 사진(`photo-…`)을 그 모임에 맞는 사진으로 바꿉니다(2-3).
4. **필요 없는 메뉴 빼기**: 해당 `<div class="page">` 블록을 지우고, `ALL_PAGES`·`GROUP`, 상단 메뉴(`.gnb`), 모바일 메뉴(`.drawer-panel`), 푸터 네 곳에서 링크를 지웁니다.
5. **분류 바꾸기**: `index.html` 스크립트의 `POST_CATS`(게시판 분류), `RES_CATS`(자료 분류), `RATINGS`(평가 항목)를 바꿉니다. **`supabase/schema.sql`의 같은 목록(check 제약)도 함께** 바꿔야 저장됩니다.
6. **새 Supabase 프로젝트**에 schema.sql을 실행합니다(5-2).
7. **수집할 정보가 다르면** `scraper/sources/`에 그 모임용 출처를 만듭니다(6-5). 필요 없으면 `scraper/`와 workflow를 지우고 `index.html`의 청빙 메뉴를 뺍니다.
8. 게시 전 점검표(5-3)를 확인합니다.

### 단체 성격별 추천 조합
| 단체·모임 | 쓸 메뉴 |
|---|---|
| 교회·선교단체 홈페이지 | 홈·소개(새 화면 추가)·자료실·예배 도구 |
| 직업군 커뮤니티(교사·간호사 등) | 정보 모음(수집기)·기관 평가·대나무숲·자료실 |
| 동아리·스터디 | 대나무숲(자유게시판으로 이름 변경)·자료실 |
